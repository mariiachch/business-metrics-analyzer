# Практическое занятие № 1. Ответы на контрольные вопросы

## 1. Чем отличается Git от GitHub?

Git является системой контроля версий, которая работает на компьютере разработчика и хранит историю изменений проекта. GitHub — облачный онлайн-сервис, где можно хранить Git-репозитории и работать над ними вместе с другими людьми.

## 2. Для чего используется виртуальное окружение Python?

Виртуальное окружение — это отдельная среда со своими библиотеками для одного проекта. Нужно для того, чтобы избежать конфликтов между разными версиями библиотек в разных проектах.

## 3. Что такое commit, branch, remote, pull request?

- Commit — сохранение изменений в истории проекта.

- Branch — ветка разработки, в которой можно работать, не затрагивая main.

- Remote — удалённый репозиторий.

- Pull request — запрос на слияние изменений из одной ветки в другую, где их можно обсудить и проверить.

## 4. Зачем нужен файл .gitignore?

В нём перечисляют файлы и папки, которые Git должен игнорировать: виртуальное окружение, файлы с паролями и временные файлы. Так в репозиторий не попадает лишнее.

## 5. Как организовать командную работу над бизнес-приложением с помощью Git?

Под каждую задачу создаётся своя ветка. Изменения коммитятся и отправляются на GitHub, затем оформляется pull request. Коллега проверяет код, оставляет комментарии, и после этого ветка сливается (merge) в main.

## 6. Какие файлы обязательно должны быть в репозитории учебного проекта?

README.md с описанием проекта, .gitignore, requirements.txt со списком библиотек, исходный код (main.py) и документация в папке docs.

## 7. Что произойдёт, если два разработчика изменят один и тот же файл в разных ветках?

Если они изменили разные места файла, Git объединит правки сам. Если одну и ту же строку, при слиянии возникнет конфликт: нужно вручную выбрать нужный вариант и сделать новый коммит.

# Практическое занятие № 2. Ответы на контрольные вопросы

## 1. Чем отличаются бизнес-требования от функциональных и нефункциональных?

Бизнес-требования описывают, чего организация хочет добиться: цели, показатели, ограничения. В нашем проекте это сокращение подготовки месячного отчёта с 2–3 дней до часа. Функциональные требования описывают, что именно должна делать система: например, загружать выгрузки из Excel и считать KPI. Нефункциональные описывают, как система должна работать: скорость, безопасность, удобство.

## 2. Каким критериям должна соответствовать качественная User Story?

Критериям INVEST: она независимая (Independent), обсуждаемая (Negotiable), ценная для пользователя (Valuable), оцениваемая (Estimable), небольшая (Small) и проверяемая (Testable). Записывается в формате «Как <роль>, я хочу <действие>, чтобы <ценность>».

## 3. Зачем нужны критерии приёмки и как они связаны с тестированием?

Критерии приёмки показывают, при каких условиях история считается выполненной, и снимают спор между заказчиком и разработчиком о том, что значит «готово». Каждый критерий в формате Given-When-Then является готовым тестовым сценарием: задано начальное состояние, действие и ожидаемый результат, поэтому по ним тестировщик пишет тесты.

## 4. Какие элементы включает Use Case-диаграмма?

Акторов, варианты использования, границу системы и связи между ними: ассоциации между актором и вариантом использования.

## 5. Что такое backlog и как он приоритизируется?

Backlog-ом называется список задач проекта, в котором у каждой есть приоритет, оценка и номер спринта. Приоритизировать можно по методу MoSCoW, по Story Points или по матрице «ценность/сложность». Чем выше бизнес-ценность задачи, тем раньше она попадает в работу.

## 6. Как связаны User Stories, Use Cases и backlog?

С помощью бизнес-требований формируются User Stories. Они собираются в backlog, где их приоритизируют и распределяют по спринтам. Use Case-диаграмма показывает те же функции с точки зрения акторов и помогает проверить, что истории покрывают все сценарии работы пользователей с системой.

## 7. Какие методы сбора требований вы знаете? В каких ситуациях они применяются?

- Интервью с заказчиком: когда нужно выяснить цели и ожидания ключевых лиц.

- Анкетирование: когда пользователей много и нужно быстро собрать мнения.

- Наблюдение за работой пользователей: когда процесс сложно описать словами.

- Анализ документов и существующих отчётов: когда процесс уже работает.

- Прототипирование: когда заказчику трудно сформулировать требования, не видя интерфейс.
